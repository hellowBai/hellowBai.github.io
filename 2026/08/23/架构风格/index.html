架构风格

Allen
2026-08-23
系统架构, 软考高级

重点

一、五大架构风格总览

常用 5 个架构风格：

  1. 调用返回风格：面向对象、分层、主程序-子程序
  2. 数据流风格：管道-过滤、批处理
  3. 独立构件风格：隐式调用（事件/C2）、进程通信
  4. 虚拟机风格：解释器、基于规则的系统
  5. 仓库风格：黑板、数据库、超文本

架构风格三要素：构件（Component，功能单元）+ 连接件（Connector，交互机制）+ 约束/拓扑。
选型本质 = 质量属性权衡，没有”最好”，只有”某个质量属性上更有优势”。

二、风格对比（质量属性矩阵）

所属风格 子风格 性能 可修改性 可扩展性 可复用性 可测试性 可维护性 安全性 一句话定位
调用返回 分层 中 强 强 中 强 强 中 层次清晰、单向依赖，如三层架构
调用返回 面向对象 中 强 强 强 中 强 中 封装/继承/多态，数据+行为内聚
调用返回 主程序-子程序 强 中 弱 中 中 弱 中 直接调用、最简单，适合中小程序
数据流 管道-过滤 弱 强 强 强 强 强 中 数据单向流动，过滤器可插拔（前提：接口稳定）
数据流 批处理 中 弱 弱 弱 中 中 中 整批一次性处理，流程固定、灵活性差
独立构件 隐式调用(事件) 中 强 强 强 弱 弱 弱 发布-订阅解耦最强，但调用链不透明
独立构件 C2 中 强 强 强 中 中 中 分层+事件结合，请求向下/通知向上
独立构件 进程通信 中 中 中 强 中 中 中 消息传递、分布式解耦
虚拟机 解释器 弱 强 强 强 中 中 中 程序+解释器，可移植
虚拟机 基于规则 弱 强 强 中 中 中 中 规则库+推理机，专家系统
仓库 黑板 弱 中 强 强 中 中 中 多知识源协同，无确定算法
仓库 数据库 中 中 中 中 强 强 强 数据集中、事务、一致性
仓库 超文本 中 中 中 中 中 中 中 节点+链接网状结构

矩阵速记规律：

  • 性能两级分化：唯一”强”是主程序-子程序；”弱”扎堆在管道、解释器、基于规则、黑板（共同点：运行时多一层间接）。
  • 可扩展性：绝大多数强，只有主程序-子程序、批处理弱（流程写死）。
  • 可测试/可维护/安全最差：隐式调用（调用链不透明）。
  • 安全性最强：数据库（事务/权限/一致性）。

三、构件与连接件

所属风格 子风格 构件（组件） 连接件（连接器） 约束/拓扑要点
调用返回 分层 各层中的模块/服务（表现层、业务层、数据层等） 层间接口调用（过程调用） 单向依赖、上层调用下层，层间解耦
调用返回 面向对象 对象 / 类（封装数据+方法） 方法调用（消息传递） 对象间通过方法调用交互，靠封装/多态
调用返回 主程序-子程序 主程序 + 子程序/过程 子程序调用（过程调用/返回） 主程序集中控制调用流程
数据流 管道-过滤 过滤器（Filter，独立处理单元） 管道（Pipe，数据传递通道） 数据单向流动，过滤器独立可插拔
数据流 批处理 各处理步骤程序 顺序文件/批次传递 整批一次性顺序执行，流程固定
独立构件 隐式调用(事件) 发布者 / 订阅者（对象、构件） 事件触发 / 事件广播（事件总线） 间接调用、订阅-发布解耦
独立构件 C2 构件（Component，层次化组件） 连接件（Connector，消息传递） request 向下（上层请求下层）、notification 向上（下层通知上层）；只能上下相邻层经连接件通信，不能越层/同层直连
独立构件 进程通信 进程（独立运行实体） 消息传递 / RPC / 套接字 / 共享内存 分布式、进程间异步通信
虚拟机 解释器 解释器引擎 + 被解释程序（指令/脚本）+ 运行状态 解释执行 / 指令调用 解释器逐条解析执行程序
虚拟机 基于规则 规则库 + 推理机（规则解释器）+ 事实/工作存储 规则匹配 / 规则触发 规则匹配-执行循环（专家系统）
仓库 黑板 黑板（中央数据结构）+ 知识源(KS) + 黑板控制器 黑板读写、控制触发 多知识源共享黑板、机会主义调度
仓库 数据库 中央数据库 + 独立访问/数据处理程序 数据库访问（SQL 查询/读写） 数据集中管理、事务、一致性
仓库 超文本 节点（文档/内容单元） 链接（超链接 Hyperlink） 节点网状组织，链接导航

连接件三类速记： 调用类（过程/方法/子程序调用）→ 消息/事件类（事件广播、消息、RPC）→ 数据共享类（管道、黑板读写、SQL、链接）。

四、典型应用场景

所属风格 子风格 典型应用场景
调用返回 分层 Web/信息管理系统（JavaEE 三层 MVC）、电商系统、企业级应用（表现层/业务层/数据层分离）
调用返回 面向对象 大多数业务系统、桌面应用、图形化系统（对象建模）、游戏对象管理
调用返回 主程序-子程序 命令行工具、批处理小工具、嵌入式简单控制程序、传统结构化程序（Fortran/C）
数据流 管道-过滤 Unix 管道命令（grep/sort/awk）、编译器流水线（词法→语法→语义）、图像处理链、ETL、信号/语音处理链
数据流 批处理 银行批量转账/对账、报表生成、离线统计、数据仓库 ETL 批处理、工资核算
独立构件 隐式调用(事件) GUI 事件处理（按钮点击）、消息中间件、微服务事件驱动、发布-订阅系统（如 Kafka）、浏览器 DOM 事件
独立构件 C2 复杂 GUI（分层+事件）、CAD、图形编辑器、分布式交互系统
独立构件 进程通信 分布式系统、微服务（RPC/REST）、操作系统进程间通信、SOA 服务交互
虚拟机 解释器 Java 虚拟机(JVM)、Python 等解释型语言运行时、脚本引擎、正则表达式引擎、浏览器 JS 引擎
虚拟机 基于规则 专家系统、规则引擎（Drools）、业务规则管理系统、诊断系统、工作流规则、智能决策系统
仓库 黑板 语音识别（HEARSAY-II）、图像理解、多专家协作诊断、AI 问题求解（无确定算法）
仓库 数据库 信息管理系统、金融交易系统、企业 ERP/CRM、一切以数据库为核心的系统
仓库 超文本 万维网(WWW)、维基百科、电子文档知识库、Web 站点导航

场景速记： 分层→企业应用；管道→流水线/Unix管道；事件→点击/发布订阅；C2→GUI分层解耦；脚本/规则可改→解释器/规则；多知识源无确定算法→黑板；数据集中事务→数据库；节点链接→超文本。

五、易混点辨析（软考最爱挖坑）

1. 隐式调用 vs C2

维度 隐式调用 C2
结构 无固定结构、平铺 严格分层
通信 事件广播、无方向 受限消息：request 向下 / notification 向上
规则 谁订阅谁响应 只能上下相邻层经连接件通信，不能越层/同层直连
可测试/可维护 弱（控制流隐式） 中（分层约束更可控）

C2 = 在”事件解耦”基础上 + 分层通信规则，弥补隐式调用”无结构、难跟踪”的缺点。

2. 黑板 vs 基于规则（专家系统的两个层面）

  • 单个专家系统 = 规则库 + 推理机 → 虚拟机（基于规则）。
  • 多个专家/知识源协作（共享黑板、机会主义调度）→ 仓库（黑板）。
  • 二者可嵌套：黑板是外层架构（多知识源如何组织），每个知识源内部往往是规则系统（虚拟机）。
  • 判断锚点：看题干是”一个知识库+推理机“（规则）还是”多个知识源共享工作区协同求解“（黑板）。

3. 管道-过滤的修改/扩展是有边界的

  • 可修改性强 = 改过滤器内部逻辑局部化（上下游无感知），前提是接口/数据格式稳定。
  • 可扩展性强 = 新增过滤器是插拔式（加环节不改已有模块）。
  • 一旦新增需求改变数据格式 / 需要共享状态 / 非顺序交互，优势消失，甚至不适合。

4. 可修改性 vs 可扩展性

  • 可修改性 = 改现有功能的成本；可扩展性 = 新增功能的成本。两者都要看”局部化程度”。

六、选型决策：需求 → 风格映射

需求特征 倾向风格
分层/前后端分离/企业应用/数据访问隔离 分层
数据流水线、分步变换、Unix 管道 管道-过滤
离线整批、流程固定 批处理
事件驱动、发布订阅、响应式解耦 隐式调用(事件)
GUI + 要分层又要解耦又要可控 C2
分布式、微服务、RPC 交互 进程通信
脚本/规则可改、可移植、运行时解释 解释器
规则库+推理、专家系统、业务规则热更 基于规则
多知识源协同、无确定算法 黑板
数据集中、事务、一致性、多系统共享 数据库
节点+链接、知识/资料组织 超文本
简单小工具、性能优先 主程序-子程序
业务对象建模、数据+行为内聚 面向对象

七、考试方向与答题模板

考法（三选一/组合）：

  1. 给场景选架构：给系统描述 → 判断用哪种风格，并说明为什么（从质量属性/构件连接件角度）。
  2. 考设计：要求画出架构、描述构件/连接件、说明约束拓扑。
  3. 考辨析/权衡：两种风格对比，或对某个质量属性的边界提问。

选型题答题模板（按此框架不丢分）：

  1. 明确结论：该系统适合采用「XX」风格。
  2. 从需求反推理由：需求 X（如新增模块不改已有）→ 该风格特征 Y（强解耦/可插拔/可扩展），至少覆盖 2 个关键质量属性。
  3. 构件 + 连接件：系统由「XX、XX、XX」等构件组成，通过「XX」连接件交互（说明方向/规则）。
  4. 权衡：说明该风格的优势与代价（如 C2 用分层约束换可控，代价是不能越层/同层直连）。
  5. 对比排除（加分）：为何不用另一风格（如”纯隐式调用难追踪”）。

记忆口诀

  • 性能弱四兄弟：管道、解释器、基于规则、黑板（运行时多一层间接）。
  • 可测试/可维护最差：隐式调用（调用链不透明）。
  • 安全性最强：数据库（事务/权限/一致性）。
  • 连接件三类：调用 / 消息事件 / 数据共享。
  • C2 方向：请求向下、通知向上（request↓ / notification↑）。
